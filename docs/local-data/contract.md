# Local data and file identity

This contract covers the local-data milestone for DA-008–010 and RT-011–014, RT-017 and RT-026. It distinguishes a working design from native evidence and release decisions.

## Storage and recovery

| Class | Location and scope | Recovery |
| --- | --- | --- |
| Originals and native metadata | Filesystem, accessed through native path and identity adapters | FolderAI reads current native metadata. Only explicit file operations may change an original. |
| User data | Local application-data directory. Embedded SQLite stores tracked references, notes and revisions, tags, favorite links, and app and per-folder preferences. | Preserve records during upgrade. Provide an internally verified pre-upgrade snapshot when crossing schema versions. |
| Operational recovery | Separate tables in the user database. One entry per operation item holds intent and proven effects needed to reconcile an interrupted change. | Finalize the reference change and the operation state in a single database transaction. Keep runtime progress and per-window undo in memory. |
| Derived data | Separate, app-owned cache location and separately versioned index. Each artifact carries provenance, content version and authorization scope, and vector data carries the embedding space. | Make stale or unauthorized data ineligible immediately. Rebuild or remove only the affected derived artifact. |
| Secrets and conversations | Provider secrets use the platform credential store. Conversations remain in memory. | Diagnostic records contain fixed event and error codes. Exclude file paths, payloads, secrets and conversations from normal logs. |

**Structured storage.** Adopt bundled SQLite for the first implementation. SQL constraints, foreign keys, conditional updates, and the Online Backup API cover the relationships and recovery paths directly. redb is an embedded transactional candidate with a native Rust key-value API. Its design would require FolderAI to implement and validate the relations and the schema migration conventions. A whole-file JSON snapshot is appropriate for a disposable fixture, where rewriting the full document and coordinating file replacement and locking are acceptable. [SQLite backup API](https://www.sqlite.org/backup.html), [rusqlite build options](https://docs.rs/crate/rusqlite/0.43.0), [redb design and API](https://docs.rs/redb/4.6.0/redb/)

Open the user store in the native application-data location. Use a serialized writer off the frontend thread, explicit transactions and enabled foreign keys on every connection. Begin with a rollback journal and full synchronization. Keep the SQLite engine version in the Cargo lockfile. A future WAL configuration requires a bundled SQLite version with the WAL reset fix and a repeat of interrupted-upgrade and concurrent-write checks. Make the native cache and user storage independently recoverable. [SQLite journaling and WAL](https://sqlite.org/wal.html)

Version the schema with `PRAGMA user_version`. On startup, check the application identifier and version before writing. Initialize only an empty database. Reject an unfamiliar, newer or corrupt store as unavailable and preserve it. For an existing supported version, create and check an Online Backup API snapshot before applying any pending schema transformations. Run all pending steps and advance the version in one transaction. An error rolls back the transaction. On restart, the database must either open at its last committed schema or surface a recovery error with the snapshot retained. A recovery copy is an explicit restore step after the source database has been preserved. If storage is unavailable, allow filesystem browsing and surface a scoped storage error when a persistence feature is used. [SQLite integrity and foreign-key checks](https://www.sqlite.org/pragma.html#pragma_integrity_check)

**Vector candidates.** Keep SQLite with `sqlite-vec` and local LanceDB as separate derived-store candidates. The first offers a small extension and SQLite deployment model with a pre-1.0 storage contract. The second exposes indexed vector search and local persistence in Rust, with an Arrow/Lance dependency and a distinct lifecycle. The selection belongs with the embedding space and index isolation tasks. Test both with the same versioned corpus, metric, model and hardware, including compatible lookup, incompatible-space rejection, incremental updates, interrupted population, cleanup, and Windows packaging. Record latency, memory, disk size and recall at the expected scale before committing to an engine. [sqlite-vec](https://github.com/asg017/sqlite-vec), [LanceDB Rust documentation](https://docs.rs/lancedb/latest/lancedb/), [embedding requirements](../../requirements/embedding.md)

## File references and reconciliation

- Treat a FolderAI item ID as an opaque durable key. Store the last proven native locator with the item, in a representation that preserves platform spelling and native encoding. A path and a native identity sample are different fields. Display labels, case folding, filename similarity, and lossy Unicode should never decide association.
- On supported volumes, use a native ID together with verified volume identity and available continuity evidence. APFS candidates are device-local file ID with volume identity and continuity during a watched interval or with an open handle. NTFS candidates are volume serial and 128-bit file ID from a handle, with watch or handle continuity. A file ID may be reused. Discontinuous history, mount replacement, uncertain birth evidence and shared native IDs such as hard links make an automatic rebind ambiguous. ExFAT, network volumes and unverified targets start with conservative behavior and support verified explicit internal operations only. [Microsoft file identity](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_id_info)
- Treat watch notifications as dirty-subtree hints. Capture a baseline after the watcher is registered, rescan affected roots when events are coalesced or lost, and compare verified samples instead of inferring delete or rename from notification pairs alone. Volume ejection, permission loss, watch overflow, incomplete scans and retryable I/O move affected items to an unresolved or unavailable state. [Apple FSEvents](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html), [Microsoft directory change API](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-readdirectorychangesw)

| Observation | Reference and metadata action |
| --- | --- |
| Verified internal rename or move | Keep the item ID. Update its locator and every affected tracked descendant using path components and verified operation results. Keep tags, notes, views and all favorite links. |
| Verified internal copy | Allocate new item IDs per successful destination. Copy that item's note and tag assignments according to the captured preference. Copy recursively only for confirmed successful entries. Preserve independent note state and skip favorite links. |
| External rename or moved subtree with evidence of continuity | Rebind exactly one tracked locator to an unambiguous observation. Keep the item ID and metadata. Apply the rule to affected tracked descendants. |
| Replacement at the same path | Treat the new object as a new item. Keep the old item's notes and tags attached to the old key. |
| Inaccessible, missing event or ambiguous match | Preserve the old association and retry a bounded reconciliation. A completed scan with reliable coverage can confirm absence. |
| Old reference conclusively unreachable after reconciliation | Remove its favorite links transactionally. Retain note and tag records against the original key. |

Capture intent and the evidence necessary to retry before each internal filesystem effect. After the native effect, commit updated locators and operation state together under a unique operation/item key. A failed commit takes the item to recovery. A retry inspects both source and destination and verifies continuity before applying the metadata update once. If the destination was replaced after the operation, retain the previous association and surface a conflict. Reconciliation handles durable recovery separately from the window's transient Undo action.

The backend currently supports one journaled move per tracked item at a time. A retained APFS or NTFS handle can prove that the original object is at the planned destination. After reopening the database without that handle, an incomplete move stays in recovery until an adapter can supply independent continuity evidence. The SQLite write and the filesystem effect are separate, so recovery never repeats the filesystem move. Normal watcher reconciliation leaves unresolved move rows to the operation recovery service. Root subscriptions use native events when available and periodic polling as a fallback. Lost events schedule a scan of registered references.

On APFS the comparison key includes the volume UUID obtained from the open descriptor, device number, inode and creation time. A tracked key at a different locator prevents allocation of a second item ID while reconciliation runs. Folder view writes carry the ID returned when the folder view loaded. A delayed save or reset against a replacement fails. Earlier path-only views and identity keys remain in SQLite for recovery. Association to a current object requires matching identity evidence.

The workspace reconciles retained references when it refreshes organization data. The cache holds up to 128 native handles and prioritizes favorite targets. Conclusive removal deletes the links and preserves personal metadata. Targets with incomplete evidence remain unavailable. Native watch hints and forced rescans were exercised separately against the reference monitor.

## Notes and organization

- Associate note save with item ID, expected revision and text as captured when the edit was made. Compare the expected revision in the write transaction. A stale revision must leave the current note intact and report a conflict with the unsaved draft preserved for review. Serialize writes for the same item in a window and never use the current selection to route a pending save.
- Start with a 350 ms debounce and a 256 KiB UTF-8 limit, subject to validating real editing flows. A selection change flushes the old item's pending edit or keeps its unsaved draft and error scoped to that item. Closing with a failed or conflicting draft requires a choice to retry, stay or explicitly discard it. Render Markdown in a sanitized preview without remote resource loads. Keep note changes separate from the original file and from AI authorization.
- Use independent favorite link IDs and optional group IDs. Reordering and group deletion update links only. Deleting a group appends its links to the root list in their previous order and preserves links even if the root already contains the same item. A tag has a unique stable ID, with optional color and flat assignments. Bulk changes inspect each selected item's current assignments, and never inherit assignments from parents. Exact duplicate tags are rejected in the write transaction. Copy-enabled operations copy assignments to the same reusable tag IDs and create independent note rows.

Schema 4 stores one copy-metadata choice per operation and records each item before staging. The transfer adapter must stage on the destination volume, bind the open staging handle with `CopyIntent::bind_staged_destination`, and retain the sealed publication through the native effect and the SQLite commit. `Store::record_completed_copy` consumes the evidence of the published object and atomically stores metadata and completion. Retry uses the same witness. `Store::recover_copy` reports pending evidence when the witness is unavailable, and `Store::fail_copy` requires the adapter to confirm that publication did not occur.

## Evidence and remaining checks

Run `python3 docs/local-data/probe.py` in the repository. On macOS 26.5.1 Apple Silicon and local APFS, Python SQLite 3.50.4 in rollback-journal mode passed backup, transactional migration rollback and retry, stale revision rejection and rebuilding a disposable derived database. Native samples matched after rename and on a moved descendant, were shared by a hard link, and differed after replacement at the same path. These tests cover the observed fixture and do not establish persistence of native identity across remount or reuse.

An optimized Rust spike on the same host inserted 100,000 synthetic note values in a single committed transaction, then verified 1,000 deterministic point lookups. Bundled SQLite 3.54.1 completed creation and insertion in 19 ms, with lookup p50/p95 of 3.04/3.46 µs and a 3,821,568-byte database. redb 4.6.0 took 68 ms, with lookup p50/p95 of 0.21/0.50 µs and a 4,460,544-byte database. This is a warm single-run comparison of simple keys. The SQLite selection relies on relational constraints and recovery support. Workload latency, peak memory and results under concurrent indexing require the representative acceptance corpus.

Migration implementation must test abrupt interruption, future or corrupt schemas, healthy backup verification and preserving notes, tags and favorites across reopen and derived rebuild. Identity implementation must exercise watcher loss, replacement during recovery, partial copy and concurrent operation outcomes. Windows native checks are pending, and DA-008–010 remain open until their acceptance evidence is complete. [Decision register](../../requirements/open-decisions.md)

On macOS APFS the Rust tests inject a deferred foreign-key error at COMMIT after a successful native rename. The old locator and operation state survive, and retry updates them once with the existing live handle. Reopening without the handle leaves the move unresolved. Replacing the destination with an independent item preserves the original metadata and favorite links. Tests also exercise watcher notification and simulated event loss. Native WebKit on the synthetic profile opened and navigated normally after schema 2 upgraded to schema 3, and the verified backup reopened at version 2. An isolated Windows x64 MSVC type check passed for the identity, watcher and storage modules. NTFS execution and packaging still require a Windows host.

The schema 4 tests cover recovery after a copy commit failure, replacement before retry, partial outcomes, stable policy across sibling entries, independent revisions and preservation of earlier copy history. Native macOS WebKit probes used isolated SQLite profiles to check note and organization persistence across launches, note flush on native close, conflict feedback and Markdown rendering with external images and unsafe links removed. The Brave fixture covered favorites drag and drop and tag filtering at 1120 × 740 and 620 × 380. The file-transfer engine still needs to call the journal at the native staging and publication boundaries. A cloned or remounted APFS volume and the Windows desktop workflow remain release checks.
